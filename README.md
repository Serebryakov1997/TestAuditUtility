# audit-file

Утилита для поиска уязвимостей в JSON- и YAML- конфигурационных файлах.

Конфигурация может быть произвольной. Результат проверки — список проблем со степенью уязвимости, расположением в конфигурации, объяснением и рекомендацией.

## Проверяемые настройки

Базовый набор проверок проекта:

| Потенциальная проблема                               | Рекомендация                                                             |
| ---------------------------------------------------- | ------------------------------------------------------------------------ |
| Логирование в debug-режиме                           | Отключить отладку и выбрать подходящий уровень логирования               |
| Пароль в открытом виде                               | Использовать хранилище секретов или ссылку на переменную окружения       |
| Использование 0.0.0.0 без ограничений                | Проверить необходимость доступа через все интерфейсы и ограничить доступ |
| Отключённый TLS                                      | Включить защищённое соединение и проверку сертификатов                   |
| Слишком широкие права доступа                        | Ограничить права необходимым минимумом                                   |
| Разрешена запись в файл другим пользователям         | Убрать ненужные права доступа к файлу                                    |
| Использование устаревших или небезопасных алгоритмов | Выбрать алгоритм, соответствующий задаче и требованиям безопасности      |

## Быстрый старт

Скачать зависимости и собрать приложение:

```bash
go mod download
go build -o audit-file ./cmd/audit-file
```

Создать пример JSON-конфигурации:

```bash
cat > config.json <<'JSON'
{
  "version": "0.1",
  "log": {
    "output": "stdout",
    "level": "debug"
  }
}
JSON
```

Запустить анализ:

```bash
./audit-file config.json
```

Для этого примера ожидается обнаружение логирования в режиме `debug`.

Без предварительной сборки:

```bash
go run ./cmd/audit-file config.json
```

## Использование

```text
audit-file [flags] <file.json|file.yaml>
audit-file --stdin [flags]
```

| Флаг             | Назначение                                             |
| ---------------- | ------------------------------------------------------ |
| `--stdin`        | Читать конфигурацию из стандартного ввода вместо файла |
| `-s`, `--silent` | Не завершаться с ошибкой из-за найденных проблем       |

### Чтение из файла

```bash
./audit-file config.json
./audit-file config.yaml
```

### Чтение из stdin

Через перенаправление:

```bash
./audit-file --stdin < config.json
```

Через пайп:

```bash
cat config.yaml | ./audit-file --stdin
```

Из командной строки:

```bash
printf '%s\n' '{"log":{"level":"debug"}}' | ./audit-file --stdin
```

При использовании `--stdin` путь к файлу указывать не нужно. Если запустить команду без перенаправления, она будет ожидать ввода; на macOS/Linux завершить ввод можно нажатием Enter, затем Ctrl+D.

### Проверка без ошибки завершения из-за найденной проблемы

```bash
./audit-file --silent config.json
./audit-file -s config.yaml
./audit-file --stdin --silent < config.json
```

## Результаты анализа

Каждая найденная проблема описывается следующими данными:

- правило, обнаружившее проблему;
- степень уязвимости: `LOW`, `MEDIUM` или `HIGH`;
- путь к настройке в конфигурации или обозначение прав доступа к файлу `@file.permissions`;
- краткое объяснение;
- рекомендация по исправлению.

Например, для уровня логирования из примера выше путь к настройке — `$.log.level`. Пример содержания сообщения:

```text
LOW: логирование в debug-режиме.
Настройка: $.log.level
Рекомендация: использовать уровень info или более строгий.
```

Отсутствие уязвимостей означает, что сработавших правил нет

## Завершение программы

### Коды завершения работы программы

| Код | Ситуация                                  | Результат                                               |
| --- | ----------------------------------------- | ------------------------------------------------------- |
| `0` | Проверка завершена, уязвимости не найдены | Выводится сообщение об отсутствии найденных уязвимостей |
| `0` | Найдены уязвимости и указан `--silent`    | Выводится отчёт с найденными уязвимостями               |
| `1` | Найдены уязвимости                        | Выводится отчёт с найденными уязвимостями               |
| `2` | Внутреняя ошибка сервера                  | Проверка завершилась не успешно                         |

## Рекурсивный анализ каталога

Команда `audit-dir` проверяет JSON/YAML-конфигурации в указанном каталоге и всех его подкаталогах. Результат выводится в виде массива отчетов в формате JSON.

### Запуск

Из корневой папки:

```bash
go run ./cmd/audit-dir ./configs
```

Или собрать отдельный бинарный файл:

```bash
go build -o audit-dir ./cmd/audit-dir
./audit-dir ./configs
```

Передаётся только один аргумент — путь к папке. Допускаются относительные и абсолютные пути; путь с пробелами нужно заключить в кавычки. Передача файла вместо каталога считается ошибкой. Флаги `--stdin` и `--silent` здесь не используются.

### Какие файлы проверяются

- `.json`, `.yaml` и `.yml`.
- Расширения проверяются без учёта регистра.
- Файлы с другими расширениями пропускаются.
- Вложенные каталоги обходятся автоматически.

Путь каждого файла в отчёте указывается относительно проверяемого каталога. Например, для `./configs/prod/app.yaml` при проверке `./configs` будет выведено `prod/app.yaml`.

### Пример проверки вложенного каталога

```bash
mkdir -p configs/nested
printf '%s\n' '{"debug":true}' > configs/nested/app.json

go run ./cmd/audit-dir ./configs
```

Пример отчёта, если в каталоге находится только этот файл:

```json
[
  {
    "path": "nested/app.json",
    "findings": [
      {
        "rule_id": "debug-enabled",
        "severity": "LOW",
        "path": "$.debug",
        "message": "Debug is enabled.",
        "recommendation": "Disable debug in work environment"
      }
    ]
  }
]
```

### Поля отчёта

| Поле       | Назначение                     |
| ---------- | ------------------------------ |
| `path`     | Путь к конфигурационному файлу |
| `findings` | Список найденных уязвимостей   |
| `error`    | Ошибка                         |

При отсутствии найденных уязвимостей список `findings` пуст.
Если поддерживаемых файлов нет, то результат — пустой массив `[]`.

## Проверка прав доступа к файлу — filecheck

Пакет `filecheck` проверяет права доступа к файлу через `os.Stat`. Проверка выполняется автоматически при запуске утилиты с указанием пути к файлу и при рекурсивном анализе каталога. Права доступа не изменяются.

| Файл                            | Назначение                                                         |
| ------------------------------- | ------------------------------------------------------------------ |
| `filecheck/permissions.go`      | Проверка прав доступа к файлу и формирование отчета по уязвимостям |
| `filecheck/permissions_test.go` | Unit-тесты `permissions.go`                                        |

### Критерии проверки

| Условие                                | Примеры прав           | Результат       |
| -------------------------------------- | ---------------------- | --------------- |
| Запись разрешена только администратору | `0600`, `0644`         | Уязвимостей нет |
| Запись разрешена группе пользователей  | `0660`, `0664`         | `MEDIUM`        |
| Запись разрешена другим пользователям  | `0606`, `0666`, `0777` | `HIGH`          |

Если запись разрешена и группе, и остальным пользователям - это уязвимость уровня `HIGH`. Во всех случаях используется `rule_id: "file-permissions"` и `path: "@file.permissions"`.

### Пример запуска

Создать отдельный тестовый каталог и конфигурацию:

```bash
permission_demo_dir=$(mktemp -d)
printf '%s\n' '{"debug":false}' > "$permission_demo_dir/app.json"
chmod 666 "$permission_demo_dir/app.json"

go run ./cmd/audit-file "$permission_demo_dir/app.json"
echo $?
```

Ожидается нахождение уязвимости `file-permissions` степени `HIGH` и код завершения `1`.

С флагом `--silent` уязвимость остаётся в отчёте, но код завершения равен `0`:

```bash
go run ./cmd/audit-file --silent "$permission_demo_dir/app.json"
echo $?
```

Проверить тот же каталог рекурсивно:

```bash
go run ./cmd/audit-file-dir "$permission_demo_dir"
```

Пример отчёта:

```json
[
  {
    "path": "app.json",
    "findings": [
      {
        "rule_id": "file-permissions",
        "severity": "HIGH",
        "path": "@file.permissions",
        "message": "File permissions 0666 allow writing by other users.",
        "recommendation": "Remove write permission for other users; review group access."
      }
    ]
  }
]
```

Убрать ненужные права доступа и повторить проверку:

```bash
chmod 600 "$permission_demo_dir/app.json"
go run ./cmd/audit-file "$permission_demo_dir/app.json"
echo $?
```

Теперь уязвимостей нет и код `0`.

## REST API

### Запуск сервера

Из корня репозитория:

```bash
go run ./cmd/audit-file serve -addr 127.0.0.1:9090
```

Или после сборки:

```bash
go build -o audit-file ./cmd/audit-file
./audit-file serve -addr 127.0.0.1:9090
```

Подкоманда `serve` запускает HTTP-сервер, а флаг `-addr` задаёт адрес и порт. Во всех примерах ниже используется `127.0.0.1:9090`. Для остановки нажмите Ctrl+C. Сервер пытается завершить активные запросы в течение 10 секунд, затем закрывает оставшиеся соединения.

При изменении исходного кода сервер нужно перезапустить. Если используется собранный бинарный файл, сначала пересоберите его.

### Проверка конфигурации

```text
POST /api/v1/audit
```

В теле запроса передаётся исходная JSON- или YAML-конфигурация. JSON-обёртка, путь к файлу на сервере и `multipart/form-data` не используются. Корневое значение конфигурации должно быть объектом или массивом.

Формат определяется заголовком `Content-Type`:

| Content-Type         | Формат |
| -------------------- | ------ |
| `application/json`   | JSON   |
| `application/yaml`   | YAML   |
| `application/x-yaml` | YAML   |
| `text/yaml`          | YAML   |

Допускаются параметры заголовка, например `application/json; charset=utf-8`. Формат ответа всегда JSON.

### Проверка rest api с помощью curl

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: application/json' \
  --data-binary '{"debug":true}'
```

Пример ответа со статусом `200 OK`:

```json
[
  {
    "rule_id": "debug-enabled",
    "severity": "LOW",
    "path": "$.debug",
    "message": "Debug is enabled.",
    "recommendation": "Disable debug in work environment"
  }
]
```

### Проверка с данными из файла

JSON:

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: application/json' \
  --data-binary @config.json
```

YAML:

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: application/yaml' \
  --data-binary @config.yaml
```

Префикс `@` означает чтение файла и подставляет его содержимое.

### Ответ без найденных уязвимостей

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: application/json' \
  --data-binary '{"debug":false}'
```

Ожидаемый ответ — `200 OK` и пустой массив:

```json
[]
```

Наличие уязвимостей также возвращает `200`: анализ успешно выполнен, а проблемы описаны в теле ответа. Код ошибки при завершении утилиты не переносится на статус ответа REST API; флаг `--silent` для API не требуется.

### Ответы API

| Статус                       | Причина                                                     |
| ---------------------------- | ----------------------------------------------------------- |
| `200 OK`                     | Успешная проверка                                           |
| `400 Bad Request`            | Некорректные данные конфигурации                            |
| `404 Not Found`              | Неизвестный путь                                            |
| `405 Method Not Allowed`     | Данный метод не поддерживается (метод отличный от POST)     |
| `415 Unsupported Media Type` | Content-Type отсутствует, некорректен или не поддерживается |
| `500 Internal Server Error`  | Внутренняя ошибка сервера                                   |

Ошибки возвращаются объектом JSON с полем `error`.

Некорректный JSON:

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: application/json' \
  --data-binary '{"debug":'
```

Ожидаемый статус — `400 Bad Request`:

```json
{ "error": "invalid configuration" }
```

Метод не поддерживается:

```bash
curl -i http://127.0.0.1:9090/api/v1/audit
```

Ожидается `405 Method Not Allowed` с заголовком `Allow: POST`.

Формат не поддерживается:

```bash
curl -i http://127.0.0.1:9090/api/v1/audit \
  -H 'Content-Type: text/plain' \
  --data-binary 'debug=true'
```

Ожидается `415 Unsupported Media Type`.

## gRPC API

Сервис принимает JSON/YAML конфигурации и возвращает список найденных проблем.

### Расположение файлов

| Путь                                   | Назначение                            |
| -------------------------------------- | ------------------------------------- |
| `grpc/proto/audit/v1/audit.proto`      | Контракт сервиса                      |
| `grpc/proto/audit/v1/audit.pb.go`      | Сгенерированные Go-типы сообщений     |
| `grpc/proto/audit/v1/audit_grpc.pb.go` | Сгенерированные интерфейсы и код gRPC |
| `grpc/api/handler.go`                  | Обработчик gRPC-запросов              |
| `grpc/api/handler_test.go`             | Unit-тесты gRPC API                   |
| `grpc/api/server.go`                   | Запуск и остановка сервера            |
| `cmd/config-audit-grpc/main.go`        | Точка входа gRPC-сервера              |

### Генерация Go-кода

Генерация требуется после изменения `.proto` или если сгенерированные файлы отсутствуют.

### Установка protoc

Компилятор `protoc` необходим для генерации кода из `.proto`-файлов.

**Linux (Ubuntu/Debian):**

```bash
sudo apt update
sudo apt install -y protobuf-compiler
```

**macOS:**

```bash
brew install protobuf
```

Проверить установку:

```bash
protoc --version
```

Для генерации Go-кода дополнительно установите плагины:

```bash
go install google.golang.org/protobuf/cmd/protoc-gen-go@latest
go install google.golang.org/grpc/cmd/protoc-gen-go-grpc@latest

export PATH="$PATH:$(go env GOPATH)/bin"
```

В контракте используется пакет `audit.v1` и Go import path:

```proto
package audit.v1;

option go_package = "github.com/serebryakov1997/utility/grpc/proto/audit/v1;auditv1";
```

Префикс Go import path должен совпадать со строкой `module` в `go.mod`.

Из корня репозитория выполнить:

```bash
protoc \
  --proto_path=grpc/proto \
  --go_out=grpc/proto \
  --go_opt=paths=source_relative \
  --go-grpc_out=grpc/proto \
  --go-grpc_opt=paths=source_relative \
  grpc/proto/audit/v1/audit.proto

go mod tidy
```

Файлы `audit.pb.go` и `audit_grpc.pb.go` создаются в одной папке с `audit.proto`.

### Запуск сервера

Из корневой папки:

```bash
go run ./cmd/config-audit-grpc --addr=127.0.0.1:50051
```

Или собрать и запустить отдельный бинарный файл:

```bash
go build -o audit-file-grpc ./cmd/config-audit-grpc
./audit-file-grpc --addr=127.0.0.1:50051
```

Флаг `--addr` задаёт адрес прослушивания. По умолчанию используется `127.0.0.1:50051`. После успешного открытия порта сервер выводит сообщение:

```text
gRPC server listening on 127.0.0.1:50051
```

Для остановки нажмите Ctrl+C. Сервер ожидает завершения активных запросов до 5 секунд, затем закрывает оставшиеся соединения. При изменении исходного кода нужно перезапустить сервер или заново сгенерировать бинарный файл.

### Метод и поля запроса

```text
audit.v1.AuditService/Audit
```

| Поле      | Тип      | Назначение                                                 |
| --------- | -------- | ---------------------------------------------------------- |
| `content` | `string` | Данные из конфигурационного файла                          |
| `format`  | `string` | `json`, `yaml` или `auto`; пустое значение означает `auto` |

В `content` передаётся содержимое документа.

Ответ — сообщение `AuditResponse`. Каждая проблема содержит `rule_id`, `severity`, `path`, `message` и `recommendation`. В `grpcurl` поле `rule_id` отображается как `ruleId`.

### Проверка через grpcurl

#### Установка grpcurl на Linux

Если Go уже установлен:

```bash
go install github.com/fullstorydev/grpcurl/cmd/grpcurl
```

Добавьте каталог с установленными двоичными файлами Go в `PATH`:

```bash
export PATH="$PATH:$(go env GOPATH)/bin"
```

Чтобы настройка сохранялась после перезапуска терминала, добавьте эту строку в `~/.bashrc` или `~/.zshrc`.

Проверьте установку:

```bash
grpcurl -version
```

После установки можно проверить доступность gRPC-сервера:

```bash
grpcurl -plaintext 127.0.0.1:50051 list
```

Установка grpcurl на macOS:

```bash
brew install grpcurl
```

Сервер включает reflection, поэтому клиент может получить описание API без `.proto`:

```bash
grpcurl -plaintext 127.0.0.1:50051 list
grpcurl -plaintext 127.0.0.1:50051 describe audit.v1.AuditService
```

Пример запроса с JSON через grpcurl:

```bash
grpcurl \
  -plaintext \
  -d '{"content":"{\"debug\":true}","format":"json"}' \
  127.0.0.1:50051 \
  audit.v1.AuditService/Audit
```

Пример структуры ответа:

```json
{
  "findings": [
    {
      "ruleId": "debug-enabled",
      "severity": "LOW",
      "path": "$.debug",
      "message": "Debug is enabled.",
      "recommendation": "Disable debug in work environment"
    }
  ]
}
```

Пример запроса с YAML через grpcurl:

```bash
grpcurl \
  -plaintext \
  -d '{"content":"debug: true\ntls:\n  enabled: false\n","format":"yaml"}' \
  127.0.0.1:50051 \
  audit.v1.AuditService/Audit
```

Пример запроса с указанием файла, используя `jq`:

```bash
jq -n --rawfile content config.json \
  '{content: $content, format: "json"}' | \
  grpcurl -plaintext -d @ \
    127.0.0.1:50051 \
    audit.v1.AuditService/Audit
```

### Пример запроса без найденных уязвимостей

```bash
grpcurl \
  -plaintext \
  -emit-defaults \
  -d '{"content":"{\"debug\":false}","format":"json"}' \
  127.0.0.1:50051 \
  audit.v1.AuditService/Audit
```

Ожидаемый ответ:

```json
{
  "findings": []
}
```

`-emit-defaults` явно показывает пустые поля. Без данного флага будет получен ответ `{}`.

### Ответы gRPC API

| Код                | Причина                                      |
| ------------------ | -------------------------------------------- |
| `OK`               | Проверка завершена успешно                   |
| `InvalidArgument`  | Пустая конфигурация, неподдерживаемый формат |
| `Internal`         | Внутренняя ошибка сервера                    |
| `Canceled`         | Запрос отменён                               |
| `DeadlineExceeded` | Истёк срок выполнения запроса                |

Пример повреждённого JSON:

```bash
grpcurl \
  -plaintext \
  -d '{"content":"{\"debug\":","format":"json"}' \
  127.0.0.1:50051 \
  audit.v1.AuditService/Audit
```

Ожидается ошибка `InvalidArgument`; список уязвимостей при возникновении ошибки в запросе не возвращается.

## Пайплайн тестирования

Конфигурация пайплайна: `.github/workflows/ci.yml`.

Предусмотрены запуски пайплайна тестирования при открытии или обновлении Pull Request в `develop`, при push в `develop`, в том числе после мерджа, и вручную через вкладку Actions.

Пайплайн использует `ubuntu-24.04` и устанавливает Go через `actions/setup-go` с настройкой `go-version-file: go.mod`.

Этапы проверки:

1. Получение исходного кода и установка Go.
2. Проверка форматирования.
3. Загрузка и проверка целостности зависимостей.
4. Статический анализ через `go vet`.
5. Тесты с `-race` и выводом покрытия.
6. Проверка сборки всех пакетов.

Проверка `Go checks` должна быть обязательной в настройках защиты `develop`, чтобы ошибки CI блокировали мердж.

## Добавление правил

При расширении данной утилиты:

1. Определить опасную настройку, условия срабатывания и допустимые исключения.
2. Добавить проверку в существующий механизм правил.
3. Задать степень уязвимости, объяснение и рекомендацию.
4. Добавить тесты на срабатывание и отсутствие ложного срабатывания.
